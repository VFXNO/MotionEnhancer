# UI detector INT8 / matrix-acceleration investigation — 2026-11-01

Follow-up: `ai-ui-matrix-2026-11-01.md` documents the separate explicit Vulkan
backend and verified WMMA shader ISA. This report's unverified-ISA statements
still apply to the DirectML/INT8 paths tested here.

## Outcome

**No INT8 activation. The original FP16 UI detector remains selected.** Both
static INT8 alternatives ran entirely through DirectML on the RX 9070 XT,
but were slower than FP16. No claim of forced matrix-unit acceleration is made:
ONNX Runtime traces establish provider placement, not the AMD driver's ISA.

Runtime improvements retained in the canonical build:

- UI inference sets `session.disable_cpu_ep_fallback=1`. Unsupported model
  nodes now fail setup rather than silently running on CPU. Existing worker
  box decoding/NMS remains CPU code; flow/depth sessions are unchanged.
- Optional `MOTION_ENHANCER_UI_PROFILE` tracing and offline profile close/path
  reporting. Disabled during normal capture and timed comparison runs.
- Offline detector runs configurable through `MOTION_ENHANCER_UI_TEST_RUNS`;
  existing 24 runs/three warmups remain the default.
- Detector JSON no longer hardcodes “FP16” when an override selects another
  graph. It reports that CPU fallback is disabled.

Matrix instruction selection is controlled by DirectML/AMD's driver. There
is no force-WMMA switch here. A low-level shader/ISA trace or hardware counter
would be needed to establish matrix-unit usage. No such claim was inferred
from GPU placement, model size, INT8 tensors or performance.

## Counterbalanced native measurements

Each comparison used two reverse-order rounds (FP16→INT8, INT8→FP16), three
held-out images, and 127 runs/group with three warmups excluded: **248 samples
per image/model**, **1,488 per comparison**, **2,976 total recorded samples**.
Eight-run ORT placement traces were separate and excluded from timing. Each
trace had eight DmlExecutionProvider events and no CPU-provider model events;
the GPU-only session guard was enabled throughout.

| Comparison / image | FP16 mean ms | INT8 mean ms | FP16 p95 ms | INT8 p95 ms |
| --- | ---: | ---: | ---: | ---: |
| QOperator / owned GUI | 1.649 | 3.075 | 2.124 | 4.013 |
| QOperator / game_001 | 1.558 | 2.961 | 2.037 | 4.019 |
| QOperator / game_007 | 1.575 | 3.009 | 1.979 | 4.016 |
| QDQ signed / owned GUI | 1.864 | 3.798 | 4.513 | 7.106 |
| QDQ signed / game_001 | 2.063 | 3.674 | 4.462 | 7.004 |
| QDQ signed / game_007 | 2.075 | 3.537 | 4.670 | 7.093 |

QOperator INT8 observed maximum: 9.541ms; QDQ INT8: 9.675ms. These are worker
wall times (inference, completion wait, proposal readback and CPU decoding),
not total frame-generation cost. Session creation, GPU input preprocessing,
capture and presentation are excluded. Gaming load was not orchestrated;
load/clock variation prevents treating these as an idle or guaranteed gaming
baseline. Different runs must not be used to claim an FP16 speedup caused by
the new guard. Neither precision establishes a 4ms total-pipeline guarantee.

### Detection agreement, not accuracy

On the held-out owned GUI, both models return the 32-region cap. QOperator
matches 27 FP16 boxes at IoU≥0.5 (matched median IoU 0.949); QDQ matches 29
(median 0.938). This measures baseline agreement, not ground-truth quality.
FP16 returns no regions in either held-out game frame. Both static variants
return zero in game_001 and one in game_007, around part of the top-left quest
text. The new region must not automatically be called either a false positive
or a validated improvement. Neither model is established as a general HUD
detector; the previously documented misses remain relevant.
